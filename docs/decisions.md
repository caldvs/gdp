# Decisions

What's been decided and still holds. Change a decision here in the same commit as the code that changes it. Don't undo one without asking Callum.

Code comments cite the two numbered decisions as ADR-0002 and ADR-0006.

## ADR-0002: Bank details stay on the lead's device

The lead's sort code, account number and name are kept in their browser, not on the server. They reach guests inside the join link's `#p=` fragment, which browsers never send to a server.

- The share flow asks for them on `/payout-account` before the QR. They're kept in `sessionStorage` (gone when the tab closes) unless the lead ticks _Remember on this device_, which uses `localStorage`. They aren't encrypted at rest.
- The guest's pay screen uses the details from the link.
- The fragment leaves the address bar as soon as the app's JavaScript runs, before anything renders (`apps/web/lib/secretFragment.ts`), and Vercel Analytics is sent URLs without a fragment (#147).
- `PUT /v1/me/payout-account` is deprecated: it validates and returns 200 but stores nothing.
- **Guests check the link's details** (#151, 4 Nov 2026). When the lead's share page shows a QR or link with bank details, their device sends the session `payoutCheck`: PBKDF2-SHA256 (100k rounds) of name, sort code, account number, Monzo and Revolut, salted with the session id. Never the details. A guest's app recomputes it from the `#p=` it got; if it doesn't match, the pay page says *These aren't Sam's bank details* and shows none of them, and a guest's share page doesn't pass them on. Sessions with no `payoutCheck` (older ones, or a lead whose device couldn't send it) show the link's details as before. This keeps ADR-0002: the server holds a slow, salted fingerprint that can't redirect a payment and isn't cheap to reverse.

Why: the server never holds data that would let someone redirect payments, and the lead doesn't need an account.

## ADR-0006: Splits by ways

A shared item (a bottle of wine) is split into `ways`, the number of people who shared it. Each sharer owes its price ÷ ways; the remainder penny goes to the lowest `userId`.

- Settings live in one `SHARE#<itemId>` row per item, with a `version` for optimistic locking and the last 10 activity entries.
- Whoever starts the split sets `ways`. People in the split can change it (`PUT /v1/sessions/{id}/shares/{itemId}`), but not below the number already in, and not once any of them has paid.
- Joining a full split adds a way. Leaving frees the spot.
- **Some of several can be split** (4 Nov 2026, Callum). On a line with more than one of something, whoever starts the split picks how many of it (`units`, default every one nobody has claimed) as well as how many ways; each person owes unit price × units ÷ ways. The rest of the line is still claimed one at a time, and a line has at most one split. On a quantity-1 line an item is claimed or split, never both.
- **Splitting someone else's dish: told, not asked** (#130, 4 Nov 2026; Callum can revisit). *Split* on a dish one person has claimed turns their claim into a 2-way split with the splitter at once; the confirm sheet says "Priya will see you're sharing it" and Priya's row then reads "split with Tom". Nobody is asked to approve it. Refused (`SHARE_PAID`) once that person has paid, so what they paid never changes. Splitting a split with no spot left joins it as one more way (as before). The split's activity records it as `split` with `fromUserId`.
- `splitShare` in the API and `sharePence` in `packages/core` must give the same answer.

## Product

- **The name is Pay Me Back** (#111, 2 Nov 2026), written as three words in every place people see it, short form included (tab titles, emails). The site is `paymeback.dev`. The logo is a coral coin whose £ rolls through €, $ and ¥ (#127).
- **Web only.** No native app. The UI is plain mobile web, deliberately not iOS-styled.
- **As few words as possible** on every screen.
- **Guests never sign in** (Callum, 4 Nov 2026, #183; built on "accounts are optional", 31 Oct). The QR opens a landing page (`POST /v1/sessions/preview`: host, venue, date, item count, total, first names of who's in; no bank details) and the guest joins with just a name (`POST /v1/sessions/guest-join`). That seats a `guest-…` user and returns a session token that works for that one session only: its claims, splits and payments, the bill it's pinned to, and `GET /v1/me` (which carries `guestSessionId`). Anything else is 401 `AUTH_MISSING`, so the guest isn't signed out of their bill. Guests aren't signed out for being idle, have no Bills, menu or email report, and the web app keeps them on their bill. Limits: 20 guest joins an hour per IP, 60 per table, 60 previews per IP every 10 minutes. Leads still sign in with an emailed code. Not built: a guest turning into an account and keeping the bill.
- **Up to 99 people** per bill (#135, 3 Nov 2026; was about 10).
- **Sign in with a 6-digit code typed in the same tab** (Callum, 4 Nov 2026; replaces the emailed link of #119 and its number matching, #138). The email's subject leads with the code ("482913 is your Pay Me Back code") so it shows in the phone's notification and can be typed without opening the email; the field uses `autocomplete="one-time-code"`, so phones can offer it, and it submits itself once 6 digits are in. Nothing opens a new tab, so where the person was going (a join link's `#p=` included) is never lost, and there's no mail-app browser or polling. `/email/start` returns a secret `requestId` the tab keeps; `/email/verify {requestId, code}` is the only way to use the code, so a code is no good without the tab that asked. Someone who starts a sign-in for another person's email (what #138 guarded against) now needs that person to read them the code, which the email says never to do. A code works once, for 15 minutes, with 5 tries (right or wrong), and only hashes are stored. The right code entered again by the same tab within 5 minutes still signs in (autofill and a tap can send it twice). Wrong codes say how many tries are left; a used-up or late one says *Code expired* with *Send a new code*. Old `/sign-in/verify` links redirect to the sign-in screen. Google sign-in was considered the same day and set aside for now.
- **Sign-in codes are limited** (2 Nov 2026; widened 4 Nov, #146): per address one every 30 seconds and at most 5 in 15 minutes, counted without `+tags` and, for Gmail, without dots; at most 20 an hour from one IP address (API Gateway's `sourceIp`); and 1000 an hour in all (`RATE_LIMITED`, 429). Stops the app being used to flood an inbox or spray addresses, which SES would count against us. Each code stands on its own: sending a new one doesn't cancel the last. Not done: Turnstile after several sends from one IP, and SES bounce/complaint alarms.
- **Sign out is everywhere** (#155, 4 Nov 2026). Session tokens carry the user row's `tokenVersion`; every request checks it (one GetItem), and *Sign out* calls `POST /v1/me/sign-out`, which bumps it, so every token the account holds, on any device, stops working. Signing out after being idle only clears this device.
- **Idle sign-out warns first** (#200, 5 Nov 2026; WCAG 2.2.1). An hour with no activity signs a signed-in person out of this device. Activity is a tap, key, touch, focus moving or scrolling (focus and scrolling are what a screen reader's browsing fires), shared across tabs. Two minutes before, a *Still there?* dialog says so, with *Stay signed in*; closing it counts too. While it's up, only that counts, so focus landing in it doesn't dismiss it. A tab that comes back after the hour is signed out with no warning. Guests are never signed out for being idle (#183).
- **Time limits are stated where they apply** (#203, 5 Nov 2026). Under the sign-in code: *Works for 15 minutes.* Under the join QR: *Works until the bill’s closed.* (joining is QR only, #182, and the QR re-encodes itself, so the bill closing is the only limit a lead sees).
- **The look is Sky** (Callum, 4 Nov 2026, #180): two quiet colours and one loud one. Sky-blue header and cloud-white page; red-orange only on each screen's main button; Anton headings (section headings smaller and grey, so the page title leads; 7 Nov). The action bar sits in the page flow, not pinned to the bottom of the view (#181). After *I've paid* a guest waits on a *Waiting for …* screen until the lead confirms (#184).
- **Paying the lead** (Callum, 4 Nov 2026; buttons changed 7 Nov): the pay page shows *Pay with Monzo* and *Pay with Revolut* when the lead has those handles, as outline buttons with each bank's mark (not solid bank colours: the amount band and *I've paid* are the screen's only solid blocks), and *I've paid* is always the last button; it asks *Are you sure you've paid?* before marking the payment sent.
- **Joining is by QR only** (Callum, 4 Nov 2026, #182). There's no code to type and no link to copy or share: the lead (or a guest) shows the QR and others scan it. The token in the QR is 128 random bits (22 base64url characters, `generateJoinCode`), so it can't be guessed; sessions opened before this keep their 6-letter code, which still resolves until they close. `/by-code` is still limited to 30 lookups every 10 minutes per user (#151).
- **Party size is for show** (#64, decided 2 Nov 2026). The lead can say how many are eating, themselves included (2–99, `expectedDiners`), on their table any time before it closes (*How many eating?*); unset on a table made without it. It only shows as "3 of 4 joined" and, once everyone's in, flags what's still unclaimed. It never changes the money maths: service is still split by what each person claims.
- **The lead collects.** Guests pay the lead by their own bank transfer and the lead marks it received. The app never holds money. Pay-by-bank (TrueLayer) was dropped for good (1 Nov 2026): no payment provider touches diner money, and Stripe takes only the lead's platform fee.
- **Trust-based payments.** Guests pay while the bill is still open for claiming. There's no lock-claims step in the UI.
- **Top-ups** (#121, decided 2 Nov 2026). What matters is that the lead knows they got everything they're owed and a guest knows they're good to leave. A guest who has paid can tap *I had something else*, claim more and pay just the difference (new items plus their share of service). Payments can overlap (a top-up before the first is confirmed), and the lead's *Received* covers whatever is sent and due at that moment. A guest is settled once nothing is due and every payment is confirmed. What anyone has paid never changes: a guest can't drop their claims below what they've sent (`ALREADY_PAID_FOR`), nobody is credited when someone else claims, and a split someone has paid for can't take more people. "Sent" means confirmed or marked as sent by the guest; a payment opened on the pay page but not sent is reused if the amount still matches, else replaced. Each guest's payments are a `payments[]` list on their participant row; `payment` is the latest state across it.
- **The lead can edit the bill at any time before close, including lines a guest has paid for** (decided 1 Nov 2026). No freeze on paid lines; the only edit refused is lowering a quantity below what's been claimed. Removing a line drops claims and splits on it.
- **Only the lead closes a bill.** Everyone paying doesn't settle it, because a late guest may still take a split seat or a leftover item. Unclaimed items go on the lead. Payments are still accepted after closing. Closing releases the bill, so the lead can edit it or share it again; the closed table keeps the version it was pinned to.
- **Scanning uses our own camera, then a photo check** (#59, #60). *Scan a bill* opens a full-screen camera with a bill-shaped guide; where the browser has no camera API or access is refused, it falls back to the phone's camera app. Every photo, taken or chosen, is shown as *All in?* with *Retake* and *Use photo*; nothing uploads until *Use photo*.
- **Nothing asked while the bill is read** (#61, 2 Nov 2026; changed 3 Nov, #135, #136). The reading screen is R2 (the photo, the bill's rows filling in) and asks nothing; Review bill opens when it's read, and Bills' *Bill read* row goes straight there. The place comes from the receipt alone (and the address lookup, #62). Party size is set on the lead's table.
- **Check these, then Review bill** (#107, 4 Nov 2026, Callum). One model, no second read: the reader notes any line it can't read clearly (`unsure`, e.g. "price faded"), and before Review bill the lead sees those lines one at a time (name, price each, quantity, the photo above) and taps *Looks right* or fixes them. The check saves once, at the end, and any amend clears the notes. When the receipt names no place, the same step ends with *Where was this?* (Skip, or type the name); skipped, it isn't asked again in that tab, and Review bill shows a *Where was this?* field instead (hint "Not on the photo. Shown to everyone."; saves on leaving it or Enter, through the bill amend; #66, 4 Nov 2026). Not mid-session: fixing a shared bill is about something specific. The reader's notes miss some misreads, so a total that doesn't add up is the other signal: when the lines don't make the printed total, Review bill (mid-session too) says *Doesn't add up* with how far off it is and *See photo*, and the notice goes as soon as the lines match.
- **Bills keep their shape** elsewhere: every line stays in place and changes state as it's claimed.
- **Claiming is in three groups** (#130, 4 Nov 2026; on the claiming screen a line moves between groups instead of staying in place): *Yours*, *Still to claim*, *Claimed by others*, each in bill order. Several of one thing are claimed a portion at a time (*Claim*, then − n +), never more than were ordered; a fully claimed multiple shows *All claimed* with no button, and a wrong count is the lead's to fix in Edit bill. A row that changes because of someone else still flashes what happened (#123). The lead uses the same list on their *Your items* tab.
- **The lead's bill is two tabs** (#131, 4 Nov 2026): *Your items* and *The table* (each person, a *Not claimed* row whose sheet lets the lead claim what's left, and *Full summary*). No bill / collected / to-collect totals.
- **The lead marks money received** (Callum, 7 Nov 2026; replaces confirming each payment the guest said they'd sent). The lead usually sees a guest's money arrive as a banking app notification, so they don't wait for the guest. Each guest's row on *The table* shows what they've claimed by name and what it comes to, live, then *Paid* or *Received*. *Received* asks once ("£25.31 from Tom? Only once it's in your account.") and settles the guest for everything due now: what they say they've sent is confirmed, a payment opened but not sent is closed, and the rest is recorded as received (`POST /v1/sessions/{id}/participants/{userId}/received`). What they say they've sent is still shown (*Says they've paid £x*) so the lead can match it to their bank. A guest who claims more afterwards owes the difference, as with any top-up. The lead lands on *Your items* until they've claimed something. *Full summary* is a plain statement like the emailed report, with *Email this* and *Copy as text*.
- **Discount lines go into the item they came from** (decided 1 Nov 2026). A minus line on the bill ("Coffee & Cannoli LRG −4.00") lowers the price of the item it belongs to, so whoever claims that item gets the discount. If the reader can't tell which item, the discount is shared across every line by price. No line is ever below £0.
- **Repeated lines become one line** (4 Nov 2026, Callum). When a receipt prints the same thing on separate lines (four "Zinfandel BTL £21.50" rows) rather than "4 Zinfandel BTL", reading the bill folds them into one line with that quantity (`mergeRepeatedLines`), so guests claim them one at a time and some can still be split (ADR-0006). Lines merge only when name (ignoring case and spacing), price each, category and course all match, wherever they sit on the receipt; a line the reader is `unsure` of stays on its own. Only the first read merges: lines the lead adds or edits are left as they are.
- **Deposits are left out of the split** (decided 1 Nov 2026). The lead usually paid the deposit, so the lead has paid the whole bill (deposit plus balance) and guests owe their full share. The bill's total is the total before the deposit comes off.
- **Bills and History show money** (5 Nov 2026). A bill's row shows the host its total and a guest their share (what the bill page says they owe, round-up included); a guest's row also names the whole bill (*· £96.00 bill*). An open guest row says *You owe £x* until paid; History ticks *Paid £x*; History's host rows say *open* until closed. Deleted bills show no money. `GET /v1/me/sessions` carries `billTotalPence` and `mySharePence` from one more BatchGet (the pinned bill versions and the caller's split rows), never a read per bill. A split's row keeps a copy of who is in it (`userIds`) so a sharer's odd penny comes out as on the bill page; splits from before 5 Nov count the caller alone and can be a penny out.
- **Each meal settles on its own.** No balances carried between meals; history is a record, not a ledger.
- **No nudging or chasing** unpaid guests.
- **Exempt accounts** (decided 1 Nov 2026; tightened 3–4 Nov, #137). Email addresses on `TABLE_FEE_EXEMPT_EMAILS` never pay the platform fee, and sign in with just their email, no code. The list is a GitHub environment **secret** only (a variable would be printed in public run logs), and prod's entry is a hard-to-guess address used only for testing live, not anyone's real email (Callum, 3 Nov 2026): knowing the address is what signs you in, so it's treated like a password. Bank details stay on the device either way.
- **Pricing** (decided 4 Nov 2026, #171; replaces the £2/£3 fee paid at the QR). Sharing a bill is free for the lead overall:
  - **One free bill a month** for every lead, credit buyers included (built 4 Nov, #139). Months are calendar months in UK time; the next one comes on the 1st. Shown as a **credit**: "Spend 1 credit & get QR code", "1 credit left".
  - **Credits:** 10 for £5 (#169). They never expire and can't be refunded; the checkout asks for consent to immediate supply. A credit makes the bill free for everyone. The free one is spent first.
  - **No credit: a £1 hold** on the lead's card at the QR (#165). Nothing is taken then.
  - **Guests round up** (decided 4 Nov 2026, replacing the split of the £1 by what each ordered, #166). On a hold, each guest's total is rounded up to the next whole pound, shown on their bill as its own *Round-up* line (a whole-pound share has none). The lead sees what each guest owes with it. At close the lead is charged the round-ups of the guests whose payment they confirmed, from the hold, so at most £1; anything over £1 stays with the lead. If guests say they've paid but the lead confirmed nobody, the whole £1 is taken. Nobody paid, nobody joined, or under Stripe's 30p minimum: the hold is released. The daily job does the same for bills still open after 6 days, before the card's hold lapses (#168).
  - Why: most guests round up when they pay a friend anyway, so pennies feel more acceptable than a fee. Making no money on small tables is fine while the app is being tested; pricing gets rethought later, and so does making the "never confirm" dodge harder. Credits mean one Stripe fee for ten bills.
  - Everything up to the QR stays free (scan, check and edit the bill, bank details). **The server enforces it** (#139): `/share` needs a hold, an exempt lead or a credit, else 402 `TABLE_FEE_REQUIRED`. **One hold, one share**: a hold pays for the session it shared and no other.
  - Screens call it the *platform fee* (#128); code, routes and `TABLE_FEE_*` settings keep the old name.
  - Built so far: the free monthly credit, the server check, the £1 hold (#165), guests' round-ups (replacing their share, #166), taking it at close (#167) the daily sweep before holds lapse (#168), and credit packs (#169).

  See [table-fee.md](table-fee.md).

- **Bill reports.** Closing a bill emails every diner what they had and paid; the lead also gets what each diner paid for. Emails should come from the site's own domain once there is one.

## Technical

- **No pull requests** (decided 1 Nov 2026). Work is committed and pushed straight to `main` after running the checks locally (`CLAUDE.md`, *Pushing to main*). A red `gate` or failed deploy on main is fixed or reverted at once. The repo is public, so Actions minutes are free. **No branch protection on `main`** (Callum, 4 Nov 2026): a team of one needs to be able to do anything; the *Protect main* ruleset was deleted.

- **`gdp` is the internal name; the product is Pay Me Back** (Callum, 6 Nov 2026, #115). The repo, `@gdp/*` packages, CDK stacks and AWS resources keep `gdp`: nobody outside sees them, and renaming a table, bucket or secret means replacing it.
- **Money is integer pence, GBP only.**
- **One DynamoDB table**, single-table design. Keys and access patterns: [architecture/data-model.html](architecture/data-model.html).
- **One Lambda** behind API Gateway serves every route. `apps/api/openapi.yaml` is the contract; client types are generated from it.
- **Bills are versioned.** Every edit writes a new `V#nnn` row plus a `LATEST` mirror. A session pins the version it started with.
- **Bill reading** is Claude Sonnet 4.6 on Bedrock, and nothing else: no fallback reader and no Google services (decided 1 Nov 2026). One model for every call, for simplicity: on the Gusto receipt Sonnet read all 44 lines right where Haiku 4.5 got 39, at about 3× the cost (~4¢ a bill), which the platform fee covers (switched 1 Nov 2026). Bedrock reads the venue's name and printed address off the bill and never guesses one.
- **Bill reads are capped at 20 a day per account** (#145, 4 Nov 2026), counting only reads that reach the model: a photo read before comes from the cache and is free. Past that, `RATE_LIMITED` (429) until midnight UTC. Stops a loop (or a stolen session) running up Bedrock costs; a real lead reads a few bills a month.
- **Bill reads are cached by image, for everyone** (Callum, 4 Nov 2026; [design](design/analysis-cache.md), step 1). What the parser read from a photo, with its venue, is kept in an `ANALYSIS#<sha256>` / `P#<model:version:promptHash>` row: no user id, 30-day TTL, written only when the read works and only if absent. Anyone who uploads the exact same bytes gets a fresh bill from it (new `billId` and item ids, `parsedFrom.source: 'cache'`) with no model call and no read counted against the daily cap; a lead's corrections live on their bill and never reach the cache. A new model, prompt version or prompt text misses it. A user's own repeat photo still returns their own bill first (`IMGHASH#`). Global rather than per user: it only matches someone holding the same bytes, who can already read the receipt. The local *Skip bill cache* bypasses it too.
- **A photo the lead has sent before goes back to their bill** (5 Nov 2026; [design](design/analysis-cache.md), step 2). The upload (and `/parse` and background reads, as `duplicate`) says where that bill stands: `versionNumber`, `amended` and `session` (the live session holding the bill, else the lead's newest session for it when that one is settled; none when abandoned). The app opens the bill's table (`/session/<id>`) for a setup, claiming, paying or settled session (a settled one shows the closed bill), else Review bill, with *Picked up where you left off* when the bill was amended (an untouched one, abandoned or not, shows nothing). A settled one first shows a sheet, *You split this at Gennaro on Sat 31 Oct*, with *Start again* and *Open* (below). Resolved per request, never cached. A guest sending the lead's photo gets a bill of their own (their hash index is their own).
- **Start again makes a new bill for the same photo** (5 Nov 2026; [design](design/analysis-cache.md), step 3). `POST /v1/bills/{billId}/fork`, owner only (anyone else gets 404). `from: 'latest'` (the default) copies the latest version, so the lead's corrections carry over; `from: 'analysis'` makes it from the current parser's cached read of the photo, reading it again (and counting against the daily cap) when there's none for today's fingerprint. The new bill gets a new `billId`, version 1, new item ids and `parsedFrom.forkedFrom: { billId, versionNumber }`, keeps the photo (`uploadId`), and takes over the photo's `IMGHASH#` row, so the next repeat opens it. The old bill and its sessions aren't touched: a settled split stays settled, with its closed bill. In the app, a repeat photo of a settled bill shows a sheet (*You split this at <venue> on <day>*, the session's day): *Start again* forks from `latest` and opens Review bill for the new bill; *Open* shows the closed bill. Escape or a tap outside closes it (on the reading page, back to Bills). The app doesn't offer `analysis` yet.
- **Venue lookup** is Amazon Location Service (Places), which fills in the full address and coordinates from what Bedrock read. Answers are cached in `VENUEQ#` rows with no expiry (decided 1 Nov 2026), so it's queried with `IntendedUse: Storage` as AWS's terms require. A failed or vague lookup leaves the venue as read off the bill. **The lookup must match the receipt exactly, or it's ignored** (Callum, 4 Nov 2026; tightens #175): only a point of interest whose name is the printed name (case, apostrophes, spacing, punctuation and "&"/"and" aside) adds its address and coordinates. A near-miss name, another business in the same building, or a bare address match leaves just what's printed; a bill with no printed name gets nothing from the lookup, and the lead is asked (above). Review bill shows the venue as one row, the name only: the looked-up address starts with the name, so showing it repeated the name on a second row (Callum, 4 Nov 2026). Cache rows from before this carry no `exact` flag and are looked up again.
- **UK VAT is included in the prices** (#176, 4 Nov 2026). A VAT line printed for information is not tax to add. When the items and service already make the printed total (within 2p), the bill's tax is 0 whatever the reader returned (`addedTaxPence`).
- **Nearby places** (#62, 2 Nov 2026) **were removed on 5 Nov 2026**: once #136 took the questions off the reading screen nothing called `GET /v1/venues/nearby`, so the route, its Amazon Location `SearchNearby` search, the `NEARQ#` cache and `useNearbyVenues` went. While it ran, the lead's position was never stored and was logged rounded to 3 decimal places at most. The place now comes from the receipt, or the lead types it.
- **Bills are read in the background** (1 Nov). `POST /v1/bills/reads` returns at once and the Lambda invokes itself to do the read (45s budget, no retries); the app polls the read and the lead can go back to Bills meanwhile. The read is its own `READ#` row; the bill is only created when the read works. The synchronous `POST /v1/bills/parse` stays, with 22s to fit under API Gateway's 30s; running out is a 504 `PARSE_TIMEOUT`.
- **Polling, not push.** Session screens poll; there are no websockets or notifications.
- **Security headers** (#150, 4 Nov 2026). The web app sends a CSP (`packages/core/src/lib/securityHeaders.ts`: its own API, S3, Stripe, Vercel Analytics), `frame-ancestors 'none'` and `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, and a Permissions-Policy allowing only the camera and location. Scripts allow `'unsafe-inline'` (nonces would make every page render per request) and `'unsafe-eval'` (the HEIC converter needs it). The API sends `hono/secure-headers`. The session token stays in `localStorage`: an HttpOnly cookie wasn't done.
- **Redirects after sign-in** go only to a path on this site (`safeInternalPath`): no `//`, `\`, control characters or their percent-encoded forms (#148).
- **No GPS in committed images** (#156): the pre-commit hook refuses staged images with a GPS position (`scripts/check-image-gps.mjs`).
