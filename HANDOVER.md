## State of main

- **The app** is the Option D web UI. The whole flow is built: scan → check the bill → bank details → platform fee (when Stripe is configured) → QR → guests claim and split → pay the lead → lead closes → everyone's emailed a report. See the [README](README.md) and [decisions](docs/decisions.md).
- **Bill reading** is Claude Sonnet 4.6 on Bedrock (both calls: finding the receipt and reading it) and nothing else: no fallback reader, no Google services. Locally it uses your `AWS_PROFILE`. The app uploads photos up to 3200px; the API asks the model where the receipt is, crops to it, and sends a long one as up to 4 overlapping parts in one call (`receiptImages.ts`, pure-JS `jpeg-js`). The model copies each line's printed total and quantity; the API works out unit prices (`splitTotal`, two lines when it doesn't divide evenly). Minus lines (deals, comps) are folded into the item they came from, or shared by price when the reader can't tell which (`discounts.ts`); deposits are left out and the total is the pre-deposit one. It runs in the background: the app uploads, calls `POST /v1/bills/reads`, and the Lambda invokes itself to read (45s budget). `/reading/[id]` polls it and opens Review bill when done; the lead can go back to Bills, which shows the read as a row (kept in this browser's storage). A failed read keeps the photo with *Try again* (same upload, no re-upload) and *New photo*. The synchronous `POST /v1/bills/parse` still works, with 22s to fit API Gateway's 30s (504 `PARSE_TIMEOUT` when it runs out).
- **Venue:** Bedrock reads the name and printed address off the bill; Amazon Location Service then fills in the full address and coordinates (`VENUE_LOOKUP=amazon-location` when deployed and locally via `.env.example`, using your `AWS_PROFILE`; `none` in tests and CI). Lookups are cached for good in `VENUEQ#` rows. The name printed on the bill always wins over the lookup's (#175: Caravan came back as the Chamber of Commerce in the same building), cached rows included. **Tax:** UK prices include VAT; when items + service already make the printed total, the bill's tax is 0 whatever the reader said (`addedTaxPence`, #176; prompt v8).
- **Loading screens:** reading a bill (#174, #185, `ReadingWait` in `Reading.tsx`) shows the photo tilted with a scan line going over it, a status line that changes by time (Finding the items → Reading the prices → Adding it all up → Long bill. Nearly there, at 0/4/9/13s), a bar that eases to 94% over 15s and fills only when the read is back, and the bill as grey rows. The read reports no progress, so it all goes by time from when it started. Review bill shows grey rows (`BillSkeleton`) while it loads. After the platform fee is paid, one status card shows confirming → paid → making the QR code; the status check asks Stripe directly if the webhook is late, and after 30 seconds the page offers *Check again* instead of spinning.
- **Deploys (#124):** `main` deploys to **test** only, hourly: **Test Deploy** (`test-deploy.yml`, :17 past) takes the newest commit with a green `gate`, diffs it against the last `test` GitHub deployment and deploys only what changed: the dev API (calls API Deploy) and/or a Vercel Preview aliased to `test.paymeback.dev` (Vercel REST API; Git deploys are off in `apps/web/vercel.json`). Pushes deploy nothing; run Test Deploy by hand to ship now. **Live** is one manual **Release** run (`release.yml`): refuses a commit without a green `gate`, deploys the prod API (reviewer, smoke test, dependency check), then paymeback.dev from the same commit, then records a `live` GitHub deployment `release-YYYY-MM-DD-n` (deployments, not tags: the Actions token can't tag a commit that changed a workflow). Dev and prod share one AWS account; each has its own OIDC deploy role, and the role stacks deploy from the prod job only (#144). Prod has no Stripe key until #79. First Release ran 4 Nov on e233cb2 (prod API and paymeback.dev deployed; its tag step failed, which is what moved recording to deployments).
- **Splits on longer lines:** some of a line with more than one of something can be split (2 of 4 bottles three ways). The split's `units` live on its `SHARE#` row (absent = 1 on older splits) and come back on `shares[].units`; `POST /shares` takes `units` when starting (default: every unit nobody has claimed). The rest of the line is still claimed one at a time, and claims, amends and completeness count the split's units. On the claim list the split is its own row (`<itemId>:split`) above the rest of the line; *Split* on a longer line asks *How many?* as well as how many ways. `ITEM_NOT_SHAREABLE` is no longer returned.

- **Sign-in is a 6-digit emailed code**, typed in the same tab (4 Nov; replaced the link and number matching of #119/#138). `/email/start` emails the code (it leads the subject, so it shows in the notification) and returns a secret `requestId`; `/email/verify {requestId, code}` answers `signedIn` / `wrong` (`attemptsLeft`) / `expired`, all 200s. 15 minutes, 5 tries, hashes only, in `SIGNIN#` rows (`src/storage/signInCodeStore.ts`, `src/services/auth/emailSignIn.ts`); the right code works again for 5 minutes for the same tab. The web field (`components/EmailSignIn.tsx`) is `one-time-code`, numeric, and submits at 6 digits. Old `/sign-in/verify` links redirect to `/sign-in/email`. Limits as before: per address (ignoring `+tags` and Gmail dots), 20 an hour per IP, 1000 an hour in total (#146). Sign out bumps `tokenVersion` on the user row and signs out every device (`POST /v1/me/sign-out`, #155). Old web builds can't sign in against the new API (and the reverse), so prod web and API must ship together (Release does). Not yet tried on a real phone: check the code shows in the iOS/Gmail notification and that Safari offers it above the keyboard.

- **Secrets** aren't in the Lambda's configuration: it gets their names (`SECRET_SOURCES`) and reads them at cold start (`src/config/runtimeSecrets.ts`), so a rotated secret needs no redeploy. A missing secret fails the smoke test and dependency check.

The web build fails without an API URL or with the wrong kind of Stripe key, and the dependency check fails on a Stripe secret key of the wrong mode.
