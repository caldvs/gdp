## State of main

- **The app** is the Option D web UI. The whole flow is built: scan → check the bill → bank details → table fee (when Stripe is configured) → QR → guests claim and split → pay the lead → lead closes → everyone's emailed a report. See the [README](README.md) and [decisions](docs/decisions.md).
- **Bill reading** is Claude Sonnet 4.6 on Bedrock (both calls: finding the receipt and reading it) and nothing else: no fallback reader, no Google services. Locally it uses your `AWS_PROFILE`. The app uploads photos up to 3200px; the API asks the model where the receipt is, crops to it, and sends a long one as up to 4 overlapping parts in one call (`receiptImages.ts`, pure-JS `jpeg-js`). The model copies each line's printed total and quantity; the API works out unit prices (`splitTotal`, two lines when it doesn't divide evenly). Minus lines (deals, comps) are folded into the item they came from, or shared by price when the reader can't tell which (`discounts.ts`); deposits are left out and the total is the pre-deposit one. It runs in the background: the app uploads, calls `POST /v1/bills/reads`, and the Lambda invokes itself to read (45s budget). `/reading/[id]` polls it and opens Review bill when done; the lead can go back to Bills, which shows the read as a row (kept in this browser's storage). A failed read keeps the photo with *Try again* (same upload, no re-upload) and *New photo*. The synchronous `POST /v1/bills/parse` still works, with 22s to fit API Gateway's 30s (504 `PARSE_TIMEOUT` when it runs out).
- **Venue:** Bedrock reads the name and printed address off the bill; Amazon Location Service then fills in the full address and coordinates (`VENUE_LOOKUP=amazon-location` when deployed and locally via `.env.example`, using your `AWS_PROFILE`; `none` in tests and CI). Lookups are cached for good in `VENUEQ#` rows. Old Google Places rows in dev are replaced on their next lookup.
- **Loading screens:** reading a bill shows the photo as a thumbnail beside the title and grey bill rows (`BillSkeleton` in `ui.tsx`), which Review bill also shows while it loads. After the table fee is paid, one status card shows confirming → paid → making the QR code; the status check asks Stripe directly if the webhook is late, and after 30 seconds the page offers *Check again* instead of spinning.
- **The dev API deploys** from `main` through GitHub Actions (OIDC). Dev and prod share one AWS account. Each has its own deploy role, trusted only by jobs in its GitHub environment; the dev job redeploys both role stacks. There's no staging. Prod (`GdpBackendProd`) is deployed and paymeback.dev (Vercel Production, `NEXT_PUBLIC_APP_ENV=prod`) talks to it; Preview and test.paymeback.dev stay on dev. Prod has its own empty table, and no Stripe key until #79, so no table fee there yet. The web app is on Vercel (`web-nqib`), with Vercel Analytics.
- **Tests and CI:** one workflow, `.github/workflows/ci.yml`, runs on every push to main (and on any PR, though work now goes straight to main) and ends in a single `gate` check. Unit, integration and the Playwright e2e suite (against `FakeApi`) all run in it. Visual baselines are CI's.
  - **Coverage:** API (unit + integration together) is at ~86% lines / 70% branches, core at ~39% / 52%. Floors are in each `vitest.config.ts` (API 85/68, core 39/50, 100% on the money files). Main's numbers live on the `coverage-baseline` branch.
  - **No pull requests** (Callum, 1 Nov 2026): work is committed and pushed straight to `main` after running the checks locally; if `gate` or the deploy fails, fix or revert on main at once. The repo is public, so Actions minutes are free.
  - Property tests (fast-check) pin the money maths: client and server agree on every split, a complete bill is charged to the penny.
  - Known bugs are written as `it.fails` (none open now): fix one and its test starts failing, so change it to `it` in the same commit.
- **Testing as several people:** local and dev builds show a test bar above the header. It signs in as alice/bob/charlie/diana or a new guest (`@test.invalid`, no code) and keeps the switch to that tab by default, so the lead and a guest can share a window. API side is `POST /v1/auth/email/test-sign-in`, on locally and on dev (`AUTH_TEST_ACCOUNTS`), off in prod (the dependency check fails if not). The sign-in page's old local-only "Dev accounts" buttons are gone; the local no-code sign-in for any email is unchanged. Locally the bar also has *Skip bill cache*: uploads and reads send `skipCache`, so a photo this account has read before goes to Bedrock again and becomes a new bill (only the local API honours it). The bar never shows on Vercel Production (`NEXT_PUBLIC_VERCEL_ENV`, set in `next.config.ts`).
- **Daily cost email:** stack `GdpCostReport` (one per account, deployed by the dev job) emails Callum (address in SSM `/gdp/cost-report-to`) at 10:00 UTC with yesterday's and the month's AWS costs by service, plus a forecast (`src/ops/costReport.ts`). Two Cost Explorer calls a day at $0.01 each. In the SES sandbox the address must stay verified.
- **After each deploy** CI runs the smoke test and the dependency check (Stripe, Bedrock, SES and test accounts off in prod, from inside the Lambda; see [docs/deploy.md](docs/deploy.md)). The `gdp-dev` dashboard has a Calls out panel timing every outside call.
- **Bad request bodies** on session routes get the contract's 400 (`INVALID_INPUT`, `requestId`, `fieldErrors`) through `validJson` (`src/middleware/validate.ts`). Bills and auth have their own hooks; other routes still use `zValidator`'s default body.
- **Secrets** aren't in the Lambda's configuration: it gets their names (`SECRET_SOURCES`) and reads them at cold start (`src/config/runtimeSecrets.ts`), so a rotated secret needs no redeploy. A missing secret fails the smoke test and dependency check.
- **Environments** are named everywhere: `APP_ENV` (API: local | dev | prod; Lambdas run `NODE_ENV=production`) and `NEXT_PUBLIC_APP_ENV` (web). The web build fails without an API URL or with the wrong kind of Stripe key, and the dependency check fails on a Stripe secret key of the wrong mode. See the Environments table in [docs/deploy.md](docs/deploy.md).
- **Scanning:** *Scan a bill* opens our own camera (`Camera.tsx`: back camera, bill-shaped guide, gallery, torch where supported), falling back to the phone's camera app when there's no camera API or access is refused. Every photo is shown as *All in?* (*Retake* / *Use photo*) before anything uploads. Not yet tried on a real iPhone and Android phone with a long receipt: if small print reads worse than with the phone's own camera, raise the resolution.
- **Look:** the tinted page (pale grey-blue `--page`, white cards; tokens in `apps/web/app/globals.css`). **Storybook** in `apps/web`: `npm run storybook -w apps/web` (port 6006); stories in `apps/web/stories/` cover `ui.tsx`, the forms, the header, the join QR and three screens. Not run in CI.
- **Exempt accounts:** emails in the GitHub environment's `TABLE_FEE_EXEMPT_EMAILS` (secret or variable, comma separated) skip the table fee (status `waived`) and sign in with no code (`/email/start` returns the session). Set it on `dev` and `prod`; it applies from the next API deploy. Link sign-in instead of codes is backlog #119.

**Claiming (#123)** is built bar one part: who has an item shows as initial avatars, a row someone else just took flashes "Sam took it" for 2s (and is announced), losing a race says who won, Pick shows "n open · £x left", and *Hide taken* folds fully-claimed rows, on guest and lead tables. Not built: *Split with Sam* after losing a race, because the API refuses to share an item one person has claimed (`CLAIM_SHARE_CONFLICT` in `addShare`); it needs an API change first.

**Top-ups (#121)** are built: a paid guest taps *I had something else*, claims more and pays the difference; the lead confirms each payment (*Says they've paid £x more*). Rules in [decisions](docs/decisions.md). Payments live as `payments[]` on the participant row (`src/services/payments/ledger.ts`, `packages/core/src/lib/ledger.ts`); old sessions with one `payment` read as one payment for what was owed.
